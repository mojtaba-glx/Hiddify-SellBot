# راهنمای امن چندزبانه‌سازی Hiddify-SellBot

این سند مرجع هر هوش مصنوعی یا توسعه‌دهنده‌ای است که قرار است در آینده چندزبانه‌سازی پروژه را ادامه دهد. قبل از تغییر کد باید این فایل خوانده شود.

## وضعیت فعلی پروژه

- پروژه باید در مسیر `/home/mojte/Hiddify-SellBot` بررسی شود.
- baseline فعلی: شاخه `main`، commit `acd1d92`، نسخه `5.2.0`.
- این baseline نسخه پایدار سرور اصلی است.
- فارسی زبان پیش‌فرض و رفتار فارسی مرجع است.
- فایل‌های locale فعلی در `locales/fa.json`، `locales/en.json` و `locales/ru.json` قرار دارند.
- سیستم ترجمه اولیه در `Shared/i18n.py` وجود دارد، اما پوشش آن عمداً محدود است.
- `.env`، توکن، دیتابیس، لاگ و فایل‌های runtime در این نسخه وجود ندارند و نباید اضافه یا commit شوند.
- هدف، چندزبانه‌سازی تدریجی همین baseline است؛ بازنویسی بزرگ قبلی نباید دوباره تکرار شود.

## هدف

اضافه‌کردن فارسی، انگلیسی و روسی فقط در لایه نمایش:

- متن پیام‌ها
- عنوان دکمه‌ها
- راهنماها و گزارش‌های قابل مشاهده

منطق خرید، تمدید، پرداخت، احراز هویت، مسدودی، دیتابیس، API پنل و callbackها باید همان رفتار قبلی را حفظ کنند.

## قانون معماری

متن قابل نمایش و مسیر اجرایی دو چیز جدا هستند.

نمونه درست:

```text
action = "buy_subscription"
label = translate("menu_buy", language)
```

نمونه نادرست:

```python
if "خرید اشتراک" in text:
    open_buy_flow()
```

handler باید `action` یا `callback_data` ثابت را بررسی کند، نه ترجمه‌ای که به کاربر نمایش داده شده است.

## قواعد اجباری

1. فارسی باید بدون تغییر محسوس در رفتار و متن پایه باقی بماند.
2. `callback_data`، action key، شناسه کاربر، شناسه سرویس و شناسه پرداخت نباید به زبان وابسته باشند.
3. کلید ترجمه باید معنایی باشد؛ مانند `menu_buy` و `renew_success`، نه یک جمله فارسی.
4. متن فارسی، انگلیسی یا روسی نباید در شرط‌های business logic استفاده شود.
5. تبدیل متن ورودی کاربر به action key فقط در لایه ورودی انجام شود.
6. placeholderهای یک کلید باید در هر سه زبان دقیقاً یکسان باشند.
7. ترجمه نباید امضای توابع، schema دیتابیس، API پنل یا ساختار پرداخت را تغییر دهد.
8. fallback فقط یک رفتار مشخص داشته باشد: زبان انتخابی، سپس فارسی.
9. متن‌های سفارشی ذخیره‌شده ادمین نباید با کلیدهای ترجمه قاطی شوند.
10. هر مرحله در commit جدا انجام شود و قبل از مرحله بعد تست شود.
11. فایل‌های `.env`، دیتابیس، لاگ، بکاپ، `venv` و cache نباید در Git قرار بگیرند.
12. قبل از هر تغییر، فهرست فایل‌ها، دلیل تغییر و ریسک آن ثبت شود.

## ترتیب پیشنهادی کار

### مرحله ۱: بررسی پایه

- `git status`، نسخه و ساختار handlerها را بررسی کن.
- مسیرهای فارسی فعلی را مستند کن.
- هیچ فایل production را overwrite یا حذف نکن.

### مرحله ۲: زیرساخت ترجمه

- `Shared/i18n.py` را نقطه واحد ترجمه نگه دار.
- کلیدهای معنایی اضافه کن.
- بررسی کلیدهای مفقود و placeholderهای ناهماهنگ بساز.
- در این مرحله منطق خرید و پرداخت را تغییر نده.

### مرحله ۳: دکمه و ورودی

- label دکمه‌ها را بر اساس زبان تولید کن.
- متن هر زبان را در ورودی به action key ثابت تبدیل کن.
- `callback_data` فعلی را حفظ کن.

### مرحله ۴: مهاجرت ربات‌ها

هر ربات جداگانه انجام و تست شود:

1. UserBot: شروع، زبان، منو، وضعیت، خرید، تست رایگان، تمدید، کیف پول و پشتیبانی
2. AdminBot: منوها، مدیریت کاربر، سرور، نود، پرداخت و گزارش‌ها
3. AgentBot: احراز هویت، منو، مشتری، پلن، کیف پول و تنظیمات
4. CustomerBot: ثبت‌نام، خرید، تمدید، سرویس و پشتیبانی

### مرحله ۵: تست

برای `fa`، `en` و `ru` بررسی شود:

- `/start` و `/language`
- منوی اصلی و دکمه بازگشت/لغو
- خرید و انتخاب پلن
- تست رایگان
- تمدید اشتراک
- کیف پول و پرداخت
- نمایش سرویس و جزئیات
- پشتیبانی
- مسدودی و ردشدن همه ورودی‌ها

همچنین syntax، JSON locale، کلیدها، placeholderها و callback data باید به‌صورت خودکار بررسی شوند.

## موارد ممنوع

- ترجمه‌کردن کل پروژه با جایگزینی کورکورانه رشته‌ها
- تغییر هم‌زمان چند ربات در یک commit بزرگ
- انتقال مستقیم بازنویسی چندزبانه قبلی
- تغییر مسیر پرداخت یا تمدید به بهانه ترجمه
- استفاده از جمله فارسی به‌عنوان کلید ترجمه
- چاپ توکن، `.env` یا اطلاعات کاربران در گزارش
- اجرای `reset --hard` یا حذف دیتابیس بدون backup معتبر

## تعریف پایان کار

کار چندزبانه زمانی کامل است که:

- زبان کاربر از دیتابیس خوانده و حفظ شود.
- تغییر زبان فقط متن و دکمه را عوض کند.
- مسیرهای business در هر سه زبان یکسان باشند.
- فارسی پیش‌فرض بدون regression کار کند.
- تست خودکار و تست دستی Telegram برای مسیرهای اصلی موفق باشد.
- هیچ خطای ترجمه، placeholder یا `Server communication error` ناشی از i18n در لاگ وجود نداشته باشد.
